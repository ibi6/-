# PayloadX v1.0 全面调试与第二版优化设计

**日期：** 2026-07-19  
**项目：** PayloadX  
**产品版本：** v1.0  
**界面标识：** UI V2（第二版界面，不代表产品 v2.0）

## 1. 目标

按照《毕业设计项目优化与调试指南》对 PayloadX 做一次可复现的完整验收，并直接修复发现的问题，而不是只输出建议。

交付结果应同时满足：

- PCAP 上传、解析、会话重组、载荷提取、告警和研判形成真实可运行闭环。
- 前端、后端、数据库、API、配置、日志和文档保持一致，不展示未实现或误导性能力。
- 输入校验、文件处理、数据库操作、异常响应和本地部署边界符合 v1.0 单机工具的安全要求。
- 关键查询和解析路径不存在明显的 N+1、无界结果集或重复任务问题。
- UI V2 保持“深海青证据工作台”方向，并在桌面、平板和手机上具备清晰的信息层级。
- 通过原生 Node.js / Python 流程完成安装、测试、Lint、生产构建、真实启动和接口验收；本机不使用 Docker。
- README、变更记录和验收报告明确说明这是第二版界面，同时产品版本仍为 v1.0。

## 2. 范围与非目标

### 2.1 本轮范围

- React 前端的全部现有路由和公共组件。
- FastAPI 的全部 `/api/v1` 接口、后台解析任务和 PCAP 解析器。
- SQLite 默认数据库路径，以及与 MySQL 配置的兼容边界。
- 上传文件、运行日志、环境变量、启动脚本和生产构建。
- README 顶部品牌展示、真实界面截图、运行说明和验收文档。

### 2.2 明确不做

- 不新增登录、鉴权、用户、角色、工作区或 SSO；这些属于 v1.1/v2.0 路线图。
- 不新增 PCAPNG、MQTT、WebSocket、规则 DSL、导出和插件体系。
- 不把单机后台线程替换成 Redis/Celery 等分布式队列。
- 不更换 React、FastAPI、SQLAlchemy、数据库或现有项目目录结构。
- 不生成论文、答辩 PPT 或与代码验收无关的材料。

## 3. 已确认的设计决策

### 3.1 产品边界

PayloadX v1.0 是本地优先、单机运行的网络取证工作台。无鉴权接口不得被描述为多用户生产系统；启动脚本和文档默认只绑定回环地址。若部署到共享网络，必须由使用者在反向代理层增加访问控制。

### 3.2 视觉方向

沿用现有 UI V2 的“深海青证据工作台”：

- 深海色侧栏承载品牌和导航，浅色纸面承载高密度调查内容。
- 青绿仅用于主操作、活动状态和关键数据，不大面积铺满页面。
- 大圆角和柔和阴影继续保留，但通过边框、背景深浅和间距区分主次，避免所有卡片同质化。
- 代码、Hex、载荷预览使用深色等宽区域，与普通说明内容形成证据层级。
- 不改成通用紫色 SaaS，也不全站暗色化。

### 3.3 兼容策略

现有路由、API 路径和返回字段优先保持兼容。新增分页或过滤参数时提供默认值；修复无效配置时明确 UI 含义，不静默改变现有数据库或删除用户文件。

## 4. 后端与数据设计

### 4.1 上传与文件安全

- 继续采用分块流式写入，内存占用与文件大小解耦。
- 同时校验扩展名、经典 PCAP 魔数和最小头长度；拒绝 PCAPNG 并给出可操作提示。
- 客户端文件名只用于展示，磁盘文件名使用服务器生成的唯一前缀；剥离路径、控制字符并限制长度。
- 上传大小以进程级环境变量为安全上限，界面配置只能在该上限以内调整。
- 任一校验、写入或数据库步骤失败时清理不完整文件，并记录不包含载荷正文或敏感路径的错误日志。
- 实际上传目录以同一份配置为准，避免 UI、环境变量和代码常量各自指向不同位置。

### 4.2 API 输入与查询

- 路径 ID 保持正整数语义；状态、级别、协议和类型参数使用允许值或规范化校验。
- 搜索文本限制长度并去除无意义空白，SQLAlchemy 始终生成参数化查询。
- 过滤在数据库查询中、`LIMIT` 之前执行，避免先截断再在 Python 中过滤导致结果缺失。
- 任务、会话、载荷、告警和日志列表都具备明确的有界结果集；在不破坏前端的前提下支持 `limit/offset`。
- 会话对应的载荷 ID 使用批量查询/分组，消除逐会话查询的 N+1。
- 所有找不到资源的接口统一返回 404；非法输入为 422/400；文件过大为 413；内部异常不向客户端暴露堆栈和绝对路径。

### 4.3 事务与后台任务

- 数据库写操作显式提交，失败时回滚；关键状态迁移写结构化操作日志。
- 同一任务在 `pending/parsing/extracting` 时不得被重复启动解析线程。
- 重新解析采用“解析成功后替换旧结果”的事务边界，避免中途失败后旧证据被提前删除。
- 后台线程异常必须把任务置为 `failed`，保存用户可理解的错误摘要，并在服务端日志保留诊断信息。
- v1.0 仍使用进程内后台线程；文档明确进程重启后任务不会自动恢复，这是已知边界而非隐藏缺陷。

### 4.4 数据库性能与一致性

- 检查任务状态、外键、协议、告警状态和时间/ID 排序字段的索引，仅对有实际查询证据的字段补充索引。
- SQLite 启用外键约束，并检查删除/重新解析时父子记录的顺序与事务一致性。
- MySQL URL 继续通过环境变量提供，不把密码写入仓库、日志或示例命令。
- 测试使用临时 SQLite 数据库和临时上传目录，不污染开发数据库与真实上传文件。

### 4.5 配置与安全响应

- Pydantic 设置为上传上限、CORS 来源、环境名称和目录提供边界校验。
- 系统设置接口只允许修改当前版本真正支持的项目；上传目录作为环境级配置展示，不伪装成热更新能力。
- CORS 使用精确来源列表，不允许通配来源与凭据组合。
- API 响应为本地敏感取证数据设置合适的 `Cache-Control`；常见安全响应头由应用或 Nginx 示例统一提供。

## 5. 前端与交互设计

### 5.1 应用壳层

- 保留桌面固定侧栏、移动抽屉和黏性页头。
- 所有导航项必须有真实路由；全局操作仅保留实际可用的上传、主题和本地模式状态。
- 移动抽屉支持 Escape、遮罩关闭、焦点可见和背景滚动锁定。
- 主内容最大宽度控制超宽屏阅读距离，1920px 下不无限拉伸。

### 5.2 页面状态

每个数据页均覆盖：

- 首次加载骨架或清晰加载状态。
- 可重试的网络/后端错误状态。
- 无数据、无搜索结果和无筛选结果的差异化空状态。
- 成功/失败操作反馈，避免按钮点击后无响应。
- 轮询任务在完成、失败或离开页面后停止，避免泄漏计时器和无效请求。

### 5.3 页面级优化

- **调查工作台：** 主指标与次指标形成层级；趋势只展示有真实依据的数据，不使用伪造百分比。
- **流量捕获：** 拖放、文件选择、前端大小/扩展名校验和后端错误一致；显示上传、解析、完成、失败的真实阶段。
- **任务详情：** 任务状态、文件信息、包/会话/载荷统计和重新解析操作清晰分组。
- **载荷列表：** 搜索、类型筛选、任务上下文和视图切换分层；查询参数与 UI 状态一致。
- **载荷详情：** 预览、Hex、ASCII、元数据可切换；长内容有边界、复制反馈和安全的纯文本渲染。
- **协议与统计：** 图表颜色来自当前主题；小数据、零数据和长协议名不破版；表格保留文字明细。
- **告警：** 级别、状态和处置操作具备确认结果和空状态。
- **设置：** 只展示真实生效项，数值输入有边界；保存失败不覆盖本地已加载值。
- **日志、功能和帮助：** 避免把路线图能力写成已实现；长表格和代码块在移动端可滚动。

### 5.4 README 第二版品牌区

- 保留自托管的 SVG Banner，优化标题、说明和视觉节奏。
- 将大批 `for-the-badge` 徽章收敛成一行核心状态，其余技术栈改为普通文本/表格，减少廉价拼贴感。
- “当前展示为第二版界面（UI V2）”放在版本说明附近，明确不等于产品 v2.0。
- 用真实运行截图替换占位表格；截图不得包含本机绝对路径、密钥或无意义调试数据。

## 6. 响应式与可访问性

验收视口：375、768、1024、1440、1920 像素宽。

- 页面根节点不得产生非预期横向滚动。
- 交互目标最小高度 44px；键盘焦点清晰可见。
- 表格在窄屏使用局部横向滚动或卡片视图，不压缩成不可读列。
- 筛选标签使用横向滚动容器，不堆叠占满首屏。
- 颜色不是风险级别、状态或选择结果的唯一表达。
- 图标按钮提供可访问名称；装饰图标从辅助技术隐藏。
- 保留 `prefers-reduced-motion`，动态效果只用于反馈，不阻碍操作。

## 7. 错误处理与日志

- 前端 API 客户端统一解析 JSON/非 JSON 错误、超时/取消和网络失败，向页面返回稳定的错误消息。
- 后端使用统一异常处理策略，客户端只得到必要信息；服务端日志包含模块、级别、时间和关联任务 ID。
- 日志不记录上传载荷正文、Token、数据库密码或完整敏感配置。
- 可恢复错误提供重试入口；不可恢复输入错误明确告诉用户如何修正。

## 8. 测试与真实验收

### 8.1 自动化测试

- 前端：导航元数据、主题、文件校验、API 请求参数和新增纯函数单元测试。
- 后端：上传边界、文件名清洗、无效 PCAP、列表过滤/分页、设置校验、任务状态、重新解析事务和解析器异常样本。
- 静态检查：`npm run lint`、TypeScript 构建、`ruff check app tests`。
- 生产构建：`npm run build`，并检查产物大小与代码分包。

### 8.2 原生全栈验收

1. 使用锁定依赖安装前端和后端环境，不调用 Docker。
2. 以临时/验收配置启动 FastAPI `127.0.0.1:8001` 与 Vite `127.0.0.1:5173`。
3. 调用健康、仪表盘、任务、会话、载荷、告警、日志、统计和设置接口。
4. 上传有效演示 PCAP，等待解析完成，核对任务计数、会话、载荷和告警关联。
5. 上传错误扩展名、PCAPNG 魔数、截断文件和超限文件，核对状态码、错误消息和临时文件清理。
6. 逐页检查全部路由、加载/空/错误状态和核心操作。
7. 在五档视口检查溢出、遮挡、点击区域、图表和表格，并保存关键真实截图。
8. 使用生产构建预览再跑一次关键读取流程，避免只验证开发服务器。

### 8.3 完成标准

- 前后端测试、Lint 和生产构建全部通过。
- 核心上传解析闭环由实际接口结果证明，不以静态代码阅读代替。
- 全部现有页面可访问，无控制台致命错误、无断链和无假按钮。
- 五档视口关键页面无非预期横向溢出、遮挡或不可操作控件。
- 文档中的命令、端口、版本、能力和限制与代码一致。
- 验收报告列出问题分级、实际修复、测试证据、剩余边界和各维度 10 分制评分。
